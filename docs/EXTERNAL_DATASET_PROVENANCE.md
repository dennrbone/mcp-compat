`6ab2bfb7da1687012c70a8acac5254f571381af8cd03d0911d393ba41e010b8f`.
Путь: `benchmark/external-mcp/`. **63 случая: 12 исторических и 51 явно
сконструированный**. Таблицы этих частей публикуются отдельно. Код серверов
создан внешними разработчиками; сценарии и отрицательные вмешательства — автором
нашего исследования. «Независимый» здесь относится к происхождению реализаций
и отделению эталона от алгоритма, а не к независимой экспертной рецензии.

Все три источника имеют MIT; полные notices сохранены с каждой версией в vendor/.

три репозитория нельзя безоговорочно считать тремя независимыми экосистемами.
Анализ чувствительности объединяет эти два источника в одну lineage-группу.

## Какие контракты и исполнения воспроизводятся

В `catalogs/` записаны настоящие `tools/list` обеих закреплённых версий.
Это повторное получение каталогов из исторического кода при зафиксированном
SDK, а не утверждение о сохранённом сетевом каталоге в день исторического commit.
Python-серверы запускаются с официальным SDK **1.30.0**, TypeScript Filesystem —
SDK **1.12.3**. Старый Calculator декорирован FastMCP текущего pinned SDK:
автоматически полученный outputSchema — свойство именно этой комбинации.

Исторические примеры: чтение файлов целиком/head/tail; SELECT и UPDATE/DELETE
в SQLite; четыре арифметических выражения. Проверяются четыре инструмента на
трёх серверах. Calculator — benign evolution, не четыре исправленных breaking
changes. Дополнительные возможности media/math в качестве новых старых вызовов
не оцениваются. Для каждого случая в public.json сохранены обе полные схемы,
старый вызов, отдельный фиксированный кандидат и начальное тестовое состояние.

## Сконструированная часть

Для каждого из трёх базовых контрактов заданы 17 вмешательств: alias имени,
optional-параметр, неизвестный required-параметр, удаление параметра, кодирование
строки массивом, enum, nested, единицы, изменение только результата, скрытый
компонент состояния, внешний ресурс, меняющиеся повторные исходы, TOCTOU,
opaque, неоднозначная привязка, потеря информации, изменение default.
Это **авторские изменения внешних контрактов/обёрток наблюдений**, а не найденные
в истории ошибки этих проектов. Они проверяют границы допуска и ложные разрешения.
Их нельзя использовать для оценки частоты таких ошибок у внешних разработчиков.

Кандидаты заданы до результатов метода по исходникам и старым входам. Это
same-candidate replay, а не новая оценка качества CodeAgent/Terra или поиска
миграции. Условия без готовых правил: RecoveryInput.context пуст. Протокол
исключает oracle/ground_truth и прочий оценочный контекст на границе загрузчика.

## Независимость эталона

1. Изучены исходные обработчики обеих версий, SQL-операции и арифметические
   выражения. Для Filesystem tail учитывается завершающая пустая строка.
2. Ожидаемые результаты и состояния явно записаны в prepare_external_dataset.py;
   они не вычисляются проверяемым верификатором или обработчиком.
3. `gold.json` хранит оценочную категорию, ожидаемое полное наблюдение и основание.
4. `load_inputs` открывает public/provenance и проверяет source-хеши, но не gold.
   Он работает даже при физическом отсутствии gold.json. Оценщик читает gold
   только после получения решения. Есть тесты подмены/утечки эталона.
5. Разметка имеет высокую уверенность **в пределах явно заданной fixture**.
   Второй независимый человек её не проверял; спорный реальный внешний эффект
   не заменяется догадкой. Полнота исходного реального production-состояния
   не заявляется.

Исходные эталоны и public.json заморожены до оценки стратегий. Исправление
обнаруженного дефекта набора потребует новой версии с сохранением этой.

## Изоляция и воспроизведение

`external_runtime.py` запускает процесс Python, а из него реальный сервер
stdio, внутри macOS sandbox. HOME, TMPDIR и разрешённые записи ограничены
одноразовой `/private/tmp/mcp-external-*`. Для SQL создаётся отдельная база с
двумя вымышленными строками; для Filesystem — два вымышленных файла. Сеть
запрещена; токены/пользовательские настройки в environment не передаются.
Имена файлов плоские. Исполняемые выражения/SQL фиксированы в наборе.

Отрицательные пробы **получили PermissionError errno 1** при чтении `.git/HEAD`,
записи вне test directory и соединении с localhost. Машинное свидетельство:
`validation/publication-isolation.json`. Сначала пробы не проходили из-за
недостаточных системных прав; чужой код до рабочей политики не выполнялся.
Одно автоматическое отклонение ошибочно истолковало `true` как доступ; повторная
проверка с явными `*_denied` и errno принята. Обход отказа не использовался.

Это ограниченный профиль для просмотренных исходников и конечных тестовых
входов. Таймаут процесса — дополнительная граница, не доказательство изоляции
произвольного враждебного кода. На другой OS необходима эквивалентная проверенная
изоляция; если её нет, исполнения NOT RUN, и контрактная проверка не считается
семантическим экспериментом.

## Протокол до нового прогона

Новый ID: `external-admission-2026-11-04`. Исторические опыты Phase 16–20 не
продолжаются и не перезаписываются. Для каждого фиксированного кандидата
собираются две независимые пробы каждой реализации на копиях одного состояния.
Исходные ответы сохраняются отдельно, включая ошибки; несовпадение ручного
эталона останавливает эксперимент, не исправляя метку по ответу метода.

- A: историческая проверка SandboxVerifier на этом же кандидате.
- B: новый EvidenceVerifier с истинным заявленным профилем наблюдений.
- C: только новая входная схема, без поведенческой проверки.
- D: независимое сравнение результата и состояния на доступном наблюдении,
  без требования надёжной декларации полноты; контроль вклада сравнения.
- E: профиль полноты выключен/недостоверен; проверяется цена отказа и
  поведение при исключении значимых наблюдений.

Дополнительно прежний полный Hybrid и Hybrid с новым verifier оцениваются
отдельно: opaque и отсутствие генератора сохраняются, не скрываются.
Сопоставимые кандидаты используются в A–E; полный Hybrid может отказаться
раньше или предложить identity, поэтому эти результаты не смешиваются.
Новых модельных/платных запросов нет.

CRR/UHR/FBR и остальные знаменатели берутся из experiments.metrics без правки.
Нулевые знаменатели остаются null. Основной bootstrap — по трём репозиториям;
чувствительность — по двум lineage-группам и leave-one-project-out. Повторы и
сконструированные варианты не являются независимыми источниками. Перестановочные
p при таком числе групп имеют очень грубую дискретность и не обосновывают
универсальное превосходство. Подготовка доверенной инфраструктуры фиксируется
как затраты данного запуска; общую стоимость внедрения ретроспективно не выдумываем.

### Уточнение исполнения до первого оценивания

Фиксируется 63 × 7 = **441 решение**, один обход. A сравнивает результат
у Filesystem/Calculator и состояние у SQLite (stateful runtime), как позволяет
прежний флаг side_effects. B сравнивает оба компонента с исходным профилем.
D использует тот же новый проверяющий, но принудительно считает предпосылки
полными/замкнутыми/однозначными/детерминированными. Это намеренно ослабленный
контроль. E принудительно задаёт complete=False; если все вызовы заблокированы,
UHR неопределён, а не равен нулю. M1_old/M1_new — настоящий Hybrid с прежним/
новым verifier **без mapper**; он может выбрать identity вместо фиксированного
кандидата, его оценки показываются отдельно от A–E.

Вызовы обработчиков действительно проходят через внешний stdio сервер в
песочнице. A выполняет одну парную пробу, B/D — две, когда профиль допускает
пробу; различие затрат публикуется, и вся разность A–B не приписывается одному
полю witness. D–B изолирует декларацию полноты при остальных равных механизмах.
После **всех** решений оценщик открывает gold, сверяет старое исполнение с
независимым ручным эталоном и проверяет допущенного кандидата двумя отдельными
пробами. Correct означает сохранение полного ожидаемого наблюдения в обеих
заранее заданных пробах этого нового опыта. Повторные пробы одного вызова не
увеличивают число сценариев/кластеров. Исторические метрики не пересчитываются;
формулы и знаменатели experiments.metrics сохраняются.

Сконструированные изменения результата/состояния накладывает явно заданная
обёртка **после настоящего ответа** зафиксированного внешнего кода. «unit» у
числового SQL-ответа умножает число на 1000, у текстового результата добавляет
маркер представления; это ограниченный отрицательный контроль, не измерение
понимания физических единиц внешним сервером. Hidden/external/ambiguous
добавляют известный оценщику компонент эффекта, исключённый из частичного
наблюдения проверяющего. Nondeterministic меняет второй исход. TOCTOU меняет
заявленное состояние между preview и replay, не имитируя production-гонку
или атомарный commit. Эти вмешательства не объявляются реальными историческими
дефектами исходных проектов.

Для witness идентификатор обработчика включает commit источника, хеш кода
обёртки, её конфигурацию и native tool; case_id и gold не включены. Файлы всех
реальных RPC, решений, оценок, времени и сводок сохраняются в новом каталоге.
Завершённый запуск проверяет весь индекс SHA-256 и больше ничего не исполняет
и не перезаписывает. При смене исходников нужен новый каталог; оборванная
история RPC с пропущенным номером отклоняется.

### Дополнительная версия 2 после первого опыта

V1 зафиксирован отдельно: 441 решение, 1158 tool-вызовов, код `e53a729b`,
данные в `experiments/external-admission-2026-11-04/`. Он не заменяется.
В нём полный Hybrid с новым verifier не применял финальный replay/state gate;
найдено одно семантическое ошибочное исполнение и два допуска TOCTOU по политике.
Кроме того, первоначальный marker смены состояния не менял files/rows у двух
серверов. Это ограничение контролей сохранено и отражается отдельно от UHR.

До повторного опыта фиксируется V2 в новом каталоге с теми же 63 public-входами,
кандидатами и неизменённым gold/digest. Добавлен общий `EvidenceVerifier.admit`;
его используют B, D и полный M1_new, а также подключение нового MCP proxy.
У D и B теперь одинаковый финальный state gate: их отличие — подтверждение
предпосылок профиля. Старые A/C/M1_old остаются контрольными алгоритмами.
TOCTOU изменяет фактический data.txt/количество SQLite; в Calculator меняется
объявленное состояние обёртки. Изменение среды относится ко **всем** методам
V2. Поэтому V1–V2 не интерпретируются как чистый эффект одного алгоритма;
парные контрасты внутри V2 сравнимы. Это дополнительный опыт после выявления
ошибки, а не слепое подтверждение на ранее не изученном наборе.

Предпосылки полноты даны оператором вручную и связаны с устройством constructed
контролей; B не обнаруживает их автоматически. E показывает также цену отказа
при отсутствии этих сведений на положительных случаях. Различие D–B измеряет
ценность **переданной информации**, не качество неизвестного классификатора
полноты. Наблюдаемая цена дополнительного replay включается в runtime/call traces.

## Исключённый исторический отрицательный кандидат и разрез CONTROL

Дополнительно изучена пара Filesystem `562feeb2817266e0d155b9e4bff54a0233557f12`
→ `18ce19763999dcf7697b00c86c3a427f01eb2919` (2026-08-28),
[исходный commit](https://github.com/modelcontextprotocol/servers/commit/18ce19763999dcf7697b00c86c3a427f01eb2919).
Новая реализация move_file запрещает перезапись существующей цели; прежняя
fs.rename её допускала. Комментарий нового исходника прямо указывает, что
старые контракт и README уже обещали отказ при существующей цели: меняется
нарушавшая спецификацию реализация. Сохранение старой перезаписи означало бы
сохранение ошибки потери данных. Поэтому кандидат **исключён из основного
CRR/UHR**, исполнение этой дополнительной пары NOT RUN. Статическое изучение
не выдаётся за эксперимент. Оно показывает границу differential testing:
наблюдаемая эквивалентность не тождественна правильности по спецификации.

В замороженном public.json четыре benign Calculator записаны с family=C1
как технической группой. Аналитический разрез явно относит исторические случаи
с одинаковым именем old/new в CONTROL: 8 исторических rename, 4 benign. Raw
данные и их digest не изменены; отдельный тест защищает это разделение.
