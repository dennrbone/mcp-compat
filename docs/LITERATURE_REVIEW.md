# Сопоставление с предшествующими работами

Дата проверки источников: 3 ноября 2026 года. Это целевой обзор ближайших
работ, а не исчерпывающий систематический обзор и не экспертиза приоритета.
Использованы первичные страницы публикаций и официальная документация.

## Поиск и границы

Запросы: `MCP tool evolution benchmark`, `MCP schema drift recovery`,
`tool call verification state simulation`, `structured output JSON Schema
benchmark`, `cluster robust inference`. Проверялись arXiv, IEEE Xplore,
официальный сайт MCP и сайт автора статистической работы в UC Davis.
Повторы одной работы объединены по идентификатору публикации. Отобраны работы
об эволюции интерфейсов, проверке вызовов и оценке состояния. Общие обзоры
агентов и коммерческие описания продуктов исключены из доказательной базы.

Методические разделы проверены по полнотекстовому HTML MCPEvol-Bench, Gecko,
TOOLVERIFIER, VerifierBench и τ-bench; для остальных работ использованы
первичные аннотации и библиографические сведения. У ToolDriftBench полный текст
IEEE недоступен через используемый доступ (HTTP 418); сравнение ограничено
официальной аннотацией. Это ограничение нельзя скрывать формулировкой
«проведён полный анализ литературы».

## Предшествующая инженерная основа

Сопоставление схем и миграция API существовали задолго до LLM. Rahm и Bernstein
разделяют методы сопоставления по структуре, элементам, данным и ограничениям.
Dig и Johnson исследуют изменения API и поддержку миграций через сведения о
рефакторингах. Поэтому ни перенос поля, ни контролируемый адаптер сами по себе
не являются новым научным результатом mcp-compat.
[Rahm, Bernstein, 2001, аннотация издателя](https://link.springer.com/article/10.1007/s007780100057),
[Dig, Johnson, 2006, авторская версия](https://dig.cs.illinois.edu/papers/JSME_API_Evolution.pdf).

Сравнение наблюдений двух реализаций связано с дифференциальным тестированием.
McKeeman описывает сопоставление результатов нескольких систем и проблему
эталона. Совпадение ошибочных реализаций может остаться незамеченным; наш
верификатор не устраняет эту общую проблему. Отличается его роль в решении
о допуске конкретной миграции и отдельный контроль источника операций.
[McKeeman, 1998, первичный текст в университетском архиве](https://www.cs.tufts.edu/comp/150FP/archive/bill-mckeeman/DifferentailTesting.pdf).

## Ближайшие работы

**MCPEvol-Bench** рассматривает динамическое изменение MCP-серверов: 11
операторов эволюции применяются к 123 серверам, оценивается выполнение задач
агентами на разных версиях. Это прямое предшествующее исследование эволюции MCP.
Наш объект уже: восстановление конкретного ранее допустимого вызова с
отдельными показателями правильного восстановления, опасного исполнения и
ложного отказа. Поэтому название внутреннего набора `evobench-1.2` не означает
авторства MCPEvol-Bench, а утверждение «первый бенчмарк эволюции MCP» исключено.
[Liu et al., 2026, полный текст](https://arxiv.org/html/2607.14642v1).

**ToolDriftBench / ToolDriftGuard** изучает устаревание семантического индекса
инструментов при изменении manifest. Предложены обнаружение дрейфа и частичное
переиндексирование. Наш прототип предполагает, что пара старого и нового
контрактов уже выбрана; поиск сервера и актуализация индекса в нём не решаются.
Методы могут дополнять друг друга. Сопоставление сделано по аннотации IEEE.
[IEEE SmartIoT, 2026, DOI 10.1109/SmartIoT70864.2026.00056](https://ieeexplore.ieee.org/abstract/document/11677805/).

**Gecko** использует симуляцию, правила и модельную обратную связь для уточнения
последовательности вызовов до реального исполнения. Сам принцип предварительной
проверки не является новым. В нашем случае проверка сравнивает наблюдаемое
поведение двух доверенных локальных реализаций для одного входа и одинаковых
копий состояния; ответы и состояние не генерируются моделью-оценщиком.
[Zhang et al., 2026, полный текст](https://arxiv.org/html/2602.19218v2).

**TOOLVERIFIER** применяет контрастные вопросы модели при выборе инструмента и
параметров. Это самопроверка генератора. В mcp-compat генератор лишь предлагает
операции, а исполнение допускается отдельным программным верификатором.
Такая граница уменьшает зависимость проверки от согласия самой модели, но
переносит доверие на корректность локальных реализаций и наблюдаемого состояния.
[Mekala et al., 2024, разделы 2.1.3–2.1.4](https://arxiv.org/html/2402.14158v2).

**ToolSandbox** оценивает вызовы с состоянием, зависимостями и промежуточными
контрольными точками. **τ-bench** сравнивает итоговую базу с целевым состоянием
и измеряет устойчивость по повторным попыткам. Эти работы поддерживают выбор
наблюдаемого состояния как объекта оценки; сравнение состояния и повторы сами
по себе не образуют новизну нашей работы.
[Lu et al., 2025](https://arxiv.org/abs/2408.04682v2),
[Yao et al., 2024, раздел 3](https://arxiv.org/html/2406.12045v1).

**JSONSchemaBench** исследует соблюдение ограничений схемы, покрытие типов
ограничений и качество структурированной генерации. Наша проверка JSON и схемы
используется как необходимое условие, после которого отдельно проверяется
поведение API. Соответствие JSON Schema не принимается за семантическую
эквивалентность.
[Geng et al., 2025](https://arxiv.org/abs/2501.10868v3).

**VerifierBench** показывает риск чрезмерно строгих генерируемых верификаторов:
отклонение неверных решений может сочетаться с отбрасыванием верных. Наш
верификатор задан программно, но этот риск остаётся причиной обязательно
публиковать ложные отказы и положительные контроли, а не только нулевой UHR.
[Yin et al., 2026, разделы 2.1 и 4](https://arxiv.org/html/2610.28679v1).

**MCP-Atlas** оценивает решение многошаговых задач с реальными MCP-серверами и
разделяет публичную и закрытую части данных. Наши локальные упрощённые API не
заменяют такую внешнюю проверку; результаты нельзя переносить на реальный
каталог серверов или общее качество агента.
[Bandi et al., 2026](https://arxiv.org/abs/2602.00933v3).

## Что можно заявлять

Работа исследует конкретное сочетание ограниченного языка миграции,
консервативных структурных правил, сравнения старой и новой реализации и отказа
при недостаточной проверяемости. Её проверяемый вклад — воспроизводимая
постановка и экспериментальное разделение источника операций и допуска к
исполнению. Контроль D1 показывает, что при наличии готовых точных операций
модель не нужна для достижения лучшего наблюдаемого восстановления.

В условии без готовых операций M1 получил 308/432 правильных восстановлений
против 144/432 у ограниченного D1, но уступил проверке тех же полных кандидатов
B2 (359/432). Нулевой наблюдаемый UHR не доказывает безопасность за пределами
стенда. Этот результат не означает превосходства над всеми
алгоритмами сопоставления: полный перебор ограниченного языка и другие
детерминированные поисковые методы в сравнении не представлены.

Не заявляются: первое исследование эволюции MCP, первая симуляция до исполнения,
универсальная безопасность произвольного API, доказанная необходимость LLM,
обобщение на несколько семейств моделей или полная адаптация произвольных
выходных схем. Текущая реализация восстанавливает входной вызов и проверяет
наблюдаемый результат/состояние; универсальный преобразователь ответов не создан.

## Методологические источники и версия протокола

Зависимость наблюдений внутри инструмента требует сохранять целые кластеры
при пересэмплировании. Число сценариев нельзя подменять числом независимых
экспериментальных единиц. Здесь используются парный кластерный bootstrap и
проверка чувствительности по областям; перестановка знака дополнительно
предполагает обменность меток методов внутри кластера. Малое число кластеров
и общие шаблоны ограничивают интерпретацию интервалов и p-значений.
[Cameron, Miller, 2015, авторская версия](https://cameron.econ.ucdavis.edu/research/Cameron_Miller_JHR_2015_February.pdf).

Актуальная на дату обзора спецификация MCP — 2026-07-28; в ней изменён
протокольный обмен, включая отказ от прежнего handshake. Испытанный прототип
закреплён на Python SDK 1.30.0 и его прежнем интерфейсе. Проверка этого SDK
не означает проверки всех возможностей новой спецификации или HTTP-развёртывания.
[Текущая спецификация MCP](https://modelcontextprotocol.io/specification/2026-07-28),
[официальное объявление изменений](https://blog.modelcontextprotocol.io/posts/2026-07-28/).
